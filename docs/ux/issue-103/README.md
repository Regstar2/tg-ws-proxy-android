# Issue #103 — макеты только экрана Telegram Worker

**Статус: дизайн на согласовании.** Android UI и сетевой runtime не изменены.

- [Вариант A: единый список Worker](worker-screen-a.html) — обзор, стратегия, список смешанного пула, действия.
- [Вариант B: протоколы отдельными группами](worker-screen-b.html) — сначала стратегия и две секции Chunk Relay / Flowseal Legacy WS, затем runtime.

Оба файла автономны, без внешних библиотек и серверов. Предназначены только для экрана **Настройки → Cloudflare → Telegram Worker / Worker Pool**: **нет** главного экрана, навигации по другим разделам, общих настроек приложения, WARP/AWG provisioning, CF Proxy Domain Pool. Точки настройки маршрутизации, DC/media, диагностика и одиночный Worker здесь отражены лишь в той мере, в которой они относятся к Telegram Worker.

## Сценарии
Переключатель «Состояние» над макетом: пусто, один Chunk Relay, один Legacy WS, смешанный пул, ошибка, несовместимость, квота/cooldown, прокси работает, все выключены, прежний одиночный режим. Демонстрируются создание, изменение, выбор, отключение, удаление, проверка, импорт, стратегия, подробности и advanced. Все операции выполняются **только в памяти страницы** и не воздействуют на реальные Worker.

## Соответствие существующим моделям
- `WorkerEndpoint`: id, name, URL, transport, enabled, priority, state, latency.
- `WorkerPoolConfig`: enabled, selectedWorkerId, selectionStrategy.
- `WorkerTransport`: `CHUNK_RELAY`, `LEGACY_WEBSOCKET`; значения без явно заданного протокола не меняются на Legacy автоматически.
- `WorkerSelectionStrategy`: MANUAL, PRIORITY, FAILOVER, ROUND_ROBIN, LOWEST_LATENCY.
- `WorkerDestinationMode`: исходный адрес, DC map, media DC fix; Flowseal DC-only, media DC/IP.
- Одиночный Worker остаётся отдельной сохранённой настройкой при отключённом пуле.
- Выбранный Worker, runtime Worker, совместимость транспорта и реальный MTProto показываются **раздельно**; HTML не выдаёт simulated probe за реальное подтверждение.
- Режимы «Только Worker / Авто» — **макетное UX-предложение**, а не утверждение о уже существующем сопоставлении настроек `NetworkRoutePolicy`. Перед Compose потребуется договориться об их точном соответствии настройкам Wi-Fi/мобильной сети.

## Сравнение
| Критерий | A: единый список | B: протоколы |
|---|---|---|
| Первый Worker | Одна точка «Добавить» | Две точки добавления по технологии |
| Смешанный пул | Компактнее | Протоколы различаются на уровне секций |
| Тип Worker | Видимая метка каждой записи | Секция + метка |
| Частое действие | Список и стратегия рядом | Действия внутри соответствующего протокола |
| Диагностика | Из блока состояния | Из блока состояния |
| Узкий экран | Короче прокрутка | Длиннее, но яснее при многих Worker |

Проверять в браузере с шириной 320–430 px, включая увеличение шрифта и работающий прокси. Автоматическую проверку интерфейса переносим в Android-этап после явного одобрения выбранной структуры.

**Не утверждать макет автоматически.** Владелец выбирает A / B либо даёт замечания, после чего отдельно выполняется Compose-реализация по #103.
