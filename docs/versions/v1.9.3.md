# v1.9.3 — Worker Selection Strategies

## Goal

Let users choose how the Worker Pool picks workers for **new** Worker WebSocket connection attempts, without moving active connections or changing `selectedWorkerId` automatically.

## In scope

- `WorkerSelectionStrategy`: MANUAL, PRIORITY, FAILOVER, ROUND_ROBIN, LOWEST_LATENCY
- `WorkerSelectionResolver` — ordered candidate list per strategy
- `WorkerPoolConfig` extensions: `selectionStrategy`, `roundRobinCursor`, `lowestLatencyMaxAgeMs`, `allowDegradedWorkers`
- Integration with `WorkerFailoverResolver` / runtime tokens / Go status export
- Minimal Worker Pool UI (radio list for strategy)
- Runtime Route Truth, Diagnostics, Diagnostic Report, persistent logs
- Unit tests for all strategies
- Version `1.9.3` (`versionCode` 44)

## Out of scope

- Worker Pool UI polish (v1.9.4)
- Weighted balancing, worker groups, country filter
- Import/export, latency charts, dashboards
- Network Profiles, MTProto, moving active WebSockets

## Constraints

- Strategy applies only to new connection attempts
- MANUAL: single selected worker, max 1 attempt, no worker-to-worker failover
- LOWEST_LATENCY uses cached `latencyMs` from health check only (no inline probe)
- Round-robin cursor updated synchronously in `WorkerPoolRepository.resolveSelectionForConnection()`
- Default strategy: **FAILOVER** (matches v1.9.2 behavior)

## Files

- `worker/WorkerSelection*.kt`, `WorkerCandidateMapper.kt`
- `WorkerPoolConfig`, `WorkerPoolPersistence`, `WorkerPoolRepository`
- `WorkerFailoverConfigBuilder`, `ConnectionRuntimeConfig`
- `RouteRuntimeState`, `WorkerPoolSettingsUi`, Diagnostics, Diagnostic Report
- `native/tgwsproxy/worker_failover.go`, `tg-ws-proxy.go`

## Manual testing

1. MANUAL: only selected worker tried; Worker 2 not used when Worker 1 fails
2. ROUND_ROBIN: multiple new connections rotate workers; active connection unchanged
3. LOWEST_LATENCY: after health check, lowest latency worker chosen; no health check during connect
4. Strategy persists after app restart
5. Diagnostic Report `[Worker Selection]` section with masked URLs

## Risks

- Round-robin under heavy parallel connects may occasionally pick same worker (best-effort sync)
- LOWEST_LATENCY falls back to FAILOVER order when no fresh latency data
- Preview/diagnostics candidate order does not advance round-robin cursor

## Done criteria

Build + tests pass; all five strategies work; selectedWorkerId unchanged; UI/report/logs show strategy; no weighted/groups/import-export.
