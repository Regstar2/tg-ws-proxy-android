# v1.10.6 - Experimental Local MTProto Proxy

## Goal

Wire `MTPROTO_EXPERIMENTAL` into service/frontend orchestration without
pretending that a real MTProto runtime is available.

## Preconditions

- v1.10.2 MTProto config/storage exists.
- v1.10.4 adapter boundary exists.
- v1.10.5 in this branch records `GO_MTPROTO_VIABLE`, but runtime startup is
  still `UNSUPPORTED_RUNTIME`; there is no `READY_NATIVE_BUILD` result.

Because no MTProto runtime is available yet, this version implements the
fail-closed path only.

## In Scope

- Replace the MTProto placeholder frontend with `MtProtoLocalProxyFrontend`.
- Route `MTPROTO_EXPERIMENTAL` service startup through:
  - config loading;
  - `MtProtoRuntimeConfig` mapping;
  - local port availability preflight;
  - `MtProtoRuntimeAdapter.start()`.
- Keep SOCKS5/WS as the default and working frontend.
- Do not overwrite saved SOCKS5 port/DC/pool settings when MTProto startup is
  attempted.
- Log selected frontend, host/port, runtime state, error code, and masked secret.
- Add focused unit tests for SOCKS5 default start, MTProto unsupported, invalid
  config, and port busy mapping.

## Out of Scope

- Go MTProto frontend implementation.
- Native/Rust build integration.
- Route integration and worker pool changes.
- Telegram MTProxy link UI.
- UI polish.

## Runtime Behavior

`SOCKS5`:

- Uses the existing `Socks5LocalProxyFrontend` and `NativeProxy` path.
- Keeps the existing route backend, worker pool, diagnostics, and metrics loop.

`MTPROTO_EXPERIMENTAL`:

- Loads `MtProtoProxyConfig` from preferences.
- Validates and maps it to `MtProtoRuntimeConfig`.
- Checks whether the configured local port can be bound.
- Calls the configured `MtProtoRuntimeAdapter`.
- With the current `UnsupportedMtProtoRuntimeAdapter`, valid config returns
  `UNSUPPORTED_RUNTIME`; invalid config returns `INVALID_CONFIG`; busy port
  returns `PORT_BUSY`.
- If MTProto startup fails while SOCKS5 is already running, the service logs the
  failure and leaves the existing SOCKS5 frontend running.

## Manual Testing

1. Fresh install or existing install starts SOCKS5/WS by default.
2. Existing SOCKS5 start/stop/reconnect still works on `127.0.0.1:1081`.
3. If `local_proxy_frontend_type_v1=mtproto_experimental` is set internally,
   startup logs `MTPROTO_EXPERIMENTAL` and fails closed with
   `UNSUPPORTED_RUNTIME` while the native runtime is absent.
4. If port `1443` is occupied, MTProto startup reports `PORT_BUSY` and does not
   stop an already running SOCKS5 frontend.
5. Diagnostic/log export must not contain the raw MTProto secret.
