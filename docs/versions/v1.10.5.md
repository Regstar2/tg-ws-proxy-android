# v1.10.5 - Go Runtime Viability Probe

## Goal

Decide whether the experimental MTProto mode can continue through the existing
Go runtime instead of immediately importing the Rust native runtime.

This version does not start an MTProto proxy, does not change the current
SOCKS5/WS runtime, and does not add Rust/native build integration.

## Preconditions

- v1.10.0 upstream audit exists.
- v1.10.1 frontend abstraction exists.
- v1.10.2 MTProto config/secret model exists.
- v1.10.3 runtime import/audit gate exists.
- v1.10.4 adapter boundary exists.

All prerequisites were present in the working tree.

## Findings

- `amurcanov/tg-ws-proxy-android/old_src_golang/tg-ws-proxy.go` contains a
  complete legacy Go MTProto local proxy reference: local listener, `dd` secret
  handling, MTProxy init decrypt, DC/media extraction, relay init generation,
  WebSocket, Cloudflare proxy, TCP fallback, start/stop exports, and stats.
- The current `native/tgwsproxy/` runtime already has a mature Go route backend,
  policy filtering, worker route, CF proxy route, TCP fallback, init DC parsing,
  init patching, message splitting, and partial stream transform hooks.
- The missing piece is not the whole MTProto protocol from scratch. The missing
  piece is a separate Go MTProxy frontend that converts a Telegram MTProxy
  client connection into the current route pipeline with per-route stream
  transforms.
- Route integration is understood but not implemented in this version. `bridgeWS`
  already has transform hooks; TCP fallback and the route/session model need a
  small explicit transform boundary before MTProxy traffic can use all routes.

## Telegram Docs Checked

- https://core.telegram.org/proxy
- https://core.telegram.org/mtproto
- https://core.telegram.org/mtproto/description
- https://core.telegram.org/mtproto/transports
- https://core.telegram.org/mtproto/mtproto-transports
- https://core.telegram.org/api/links
- https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1proxy_type_mtproto.html

The official docs match the upstream/reference direction used here:

- MTProto proxies require server, port, and secret.
- MTProxy links use `t.me/proxy?server=...&port=...&secret=...` or
  `tg://proxy?...`.
- TDLib stores the MTProto proxy secret as a hexadecimal string.
- MTProxy obfuscation uses a 16-byte secret, with a common 17-byte form where
  the first byte selects the transport such as padded intermediate.
- WebSocket MTProto transport requires the `Sec-WebSocket-Protocol: binary`
  handshake header and treats WebSocket messages as a duplex byte stream.

## Decision

Status: GO_MTPROTO_VIABLE

Reason:

- Sufficient Go/reference code exists.
- The current Go runtime already owns the route backend that MTProto needs.
- A Go frontend avoids Rust/cargo-ndk and shared library name collision.
- The implementation can be isolated behind `MTPROTO_EXPERIMENTAL` while SOCKS5
  remains the default.

Limits:

- Old upstream Go is legacy/reference-only and must not be imported wholesale
  without adaptation.
- `ee` fake TLS is not part of the minimal path.
- Route integration must be implemented and tested before runtime startup is
  enabled.

## Next Version

v1.10.6 should add a Go MTProto frontend skeleton behind the existing adapter:

- add MTProxy handshake/secret parsing as isolated Go package/functions;
- add a separate local MTProto listener/controller path;
- map `MtProtoProxyConfig` into Go runtime config without changing SOCKS5;
- add route stream transform hooks for direct, CF proxy, Worker, and TCP;
- add focused Go tests for secret validation, init decrypt, DC/media extraction,
  relay init generation, transform round-trip, and route dispatch.

## Status

GO_MTPROTO_VIABLE:

- Go path is viable as a next implementation direction.

LIMITED_ROUTE_INTEGRATION_UNIMPLEMENTED:

- Route integration is designed but not implemented in v1.10.5.

UNSUPPORTED_RUNTIME:

- MTProto runtime startup remains unsupported until a real Go frontend is added.
