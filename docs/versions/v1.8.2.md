# v1.8.2 — Route Probe Core

## Goal

Add an internal **Route Probe Core** layer that checks route candidates and returns structured results (not ad-hoc strings), without changing active routing or the proxy service.

## In scope

- Models: `RouteProbeTarget`, `RouteProbeStatus`, `RouteProbeStep`, `RouteProbeErrorCode`, `RouteProbeResult`, `RouteProbeConfig`
- `RouteProbeRunner` — DNS / TCP / TLS / HTTP / WebSocket steps per target
- `RouteProbeStatusAggregator` — single place for final status rules
- `RouteDiagnosticsRepository` — run and store last results
- `RouteProbeDiagnosticsState` — UI state (does not touch Go `activeRoute`)
- Structured logs via `RouteProbeLogger`
- Minimal UI: **Check routes** in connection metrics card
- Unit tests for status aggregation
- Version `1.8.2` (`versionCode` 38)

## Out of scope

- Diagnostics screen (v1.8.3), Worker Pool, persistent logs, Telegram Media Diagnostics, auto-switching routes from probe results.

## Architectural constraints

- Probe runs on `Dispatchers.IO` with per-step and overall timeouts.
- Probe does **not** update `RouteRuntimeState` active/selected routes from Go.
- Reuses `UpstreamDiagnosticsSsl` (diagnostics-only trust model), separate sockets from live proxy.

## Manual testing

1. Enable in-app metrics → **Check routes**.
2. Worker-first + dead worker → worker probe FAIL/TIMEOUT; active route unchanged.
3. Airplane mode → `NETWORK_UNAVAILABLE` or FAIL, no crash.
4. Logcat: `Route probe started/finished`, step success/failed lines.

## Risks

- Probes open short-lived connections; may be blocked on some networks.
- VPN detection is informational (extra fail step when VPN transport present).
- Legacy `EffectiveRouteConnectionDiagnostics` remains in Settings; core probe is separate.
