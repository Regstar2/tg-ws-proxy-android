# v1.10.3 - MTProto Runtime Import Gate

## Goal

Decide whether the audited upstream MTProto runtime can be imported into the
current project, and document the exact source, build, API, route, and license
constraints before any production code is touched.

## In Scope

- Recheck local upstream clone status and commit hashes.
- Select the real runtime candidate.
- Confirm license compatibility.
- Document files/directories that would be needed for a future import.
- Document files/directories that must not be imported.
- Record build-system, JNI/FFI, route-hook, and logging/config mapping risks.

## Out of Scope

- Gradle changes.
- Native source changes.
- Production app code changes.
- Runtime service changes.
- UI changes.
- Importing source or prebuilt `.so` files.

## Decision

The selected runtime source is the Rust runtime from
`amurcanov/tg-ws-proxy-android`.

Flowseal is reference-only because it is Python desktop/server code without an
Android JNI/FFI bridge.

The upstream `old_src_golang/` core is not selected because the upstream README
states the core was rewritten in Rust and Go is no longer maintained.

Current TGWSProxyAndroid's Go runtime remains the default SOCKS5/WS backend. It
is not a compatible local MTProto frontend import target.

Gate result:

- [x] READY_TO_IMPORT
- [ ] BLOCKED_LICENSE
- [ ] BLOCKED_BUILD_SYSTEM
- [ ] BLOCKED_NO_RUNTIME_HOOK
- [ ] REFERENCE_ONLY

## Ready Scope and Limits

- `READY_TO_IMPORT` is limited to a minimal source snapshot for the v1.10.5
  native build probe.
- It does not approve production runtime startup.
- It does not approve route-integrated MTProto.
- Upstream `build_so.bat` remains reference-only: it uses a placeholder SDK
  path, installs `cargo-ndk` imperatively, builds only two ABIs, and outputs
  `libtgwsproxy.so`, which collides with the current Go runtime library.
- The Rust runtime exposes a usable C/JNA API, but it must be adapted behind a
  separate library name and Kotlin adapter.
- No route hook, injectable dialer, route callback, shared route backend, or
  current `NetworkRoutePolicy` token parser was found.
- The Rust runtime has direct WSS, Cloudflare proxy, and TCP fallback paths, but
  no current-app Cloudflare Worker route.

## Manual Testing

No runtime behavior changed in this gate version. Manual follow-up is only
needed after a future implementation changes native build or runtime startup.

Before any future import:

1. Verify Rust/cargo-ndk build on a clean machine.
2. Verify the MTProto library uses a non-conflicting shared library name.
3. Verify current SOCKS5/WS mode still starts and routes direct, worker,
   cf_proxy, and tcp on mobile and Wi-Fi.
4. Verify MTProto mode is clearly route-limited unless route hook work is done.
