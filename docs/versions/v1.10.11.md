# v1.10.11 — MTProto Diagnostics and Comparison

## Goal

Add one read-only diagnostics view for the stable SOCKS5/WebSocket frontend and
the experimental MTProto frontend without changing route selection or runtime
behavior.

## Diagnostics blocks

The Diagnostics screen and exported report now distinguish:

- `SOCKS5 / WebSocket frontend`;
- `MTProto frontend`;
- `Route backend`;
- `Worker pool / future worker pool`;
- `Runtime route truth`;
- `SOCKS5/WS vs MTProto`.

MTProto diagnostics use `GetMtProtoProxyStatus()` as the runtime source for:

- local listener state;
- outbound capability;
- selected and actual backend;
- fallback flag;
- route reason;
- sanitized last-error state;
- secret fingerprint produced by the native runtime.

The full secret is never added to the diagnostics model or report. Configuration
diagnostics expose only `CONFIGURED_MASKED`, `NOT_CONFIGURED`, or `INVALID`.

## Honest support states

`READY`, `LIMITED`, and `UNSUPPORTED` describe integration capability, not
network reachability:

- SOCKS5/WS route integration remains `READY`.
- An MTProto listener with `OUTBOUND_UNSUPPORTED` is `UNSUPPORTED`.
- The current MTProto `direct_tcp` and `cf_worker_ws` connectors are `LIMITED`
  because they do not provide parity with the shared SOCKS5 route selector,
  Cloudflare Proxy route, or full Worker pool behavior.
- MTProto diagnostics do not emit route `READY` for these partial connectors,
  even after a successful connection.

The project has no reliable persisted timestamp for the last successful MTProto
start. v1.10.11 therefore omits that value instead of inferring it from logs or
configuration.

## Source check

The diagnostics terminology and secret/link expectations were checked against:

- https://core.telegram.org/proxy
- https://core.telegram.org/mtproto
- https://core.telegram.org/mtproto/description
- https://core.telegram.org/mtproto/transports
- https://core.telegram.org/mtproto/mtproto-transports
- https://core.telegram.org/api/links
- https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1proxy_type_mtproto.html
- https://github.com/Flowseal/tg-ws-proxy
- https://github.com/amurcanov/tg-ws-proxy-android

Telegram documents MTProxy secrets as hexadecimal and proxy links as
`t.me/proxy` or `tg://proxy` with `server`, `port`, and `secret`. The route
backend is an application integration detail and is therefore reported only
from native runtime truth.

## Tests

Coverage includes:

- MTProto secret masking;
- unsupported outbound state;
- frontend kinds in report output;
- `LIMITED` route support never rendered as `READY`.

## Runtime impact

None. This version does not change:

- native routing;
- route selector or policies;
- Worker pool selection;
- secret storage;
- the default SOCKS5 frontend.
