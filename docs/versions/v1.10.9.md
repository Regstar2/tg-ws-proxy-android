# v1.10.9 - Go Route Integration Feasibility

## Goal

Determine whether the experimental Go MTProto frontend can enter the existing
route system through a real, DC-aware outbound hook without changing the
stable SOCKS5/WS runtime.

## Preconditions

- v1.10.7 provides a local-only Go MTProto listener.
- v1.10.8 exposes the listener as an experimental, limited frontend.
- The production SOCKS5/WS route pipeline provides direct WS, Worker WS, CF
  proxy WS, TCP fallback, policy filtering, and route diagnostics.

Preconditions are present.

## Findings

- The SOCKS5 handler owns destination parsing, the 64-byte init read,
  `initSession` creation, and direct-WS dispatch.
- `runRouteChain` is a real route dispatcher, but it accepts the private
  SOCKS5-oriented `initSession`; it is not an injected dialer.
- The current MTProto frontend only accepts and closes local connections with
  `OUTBOUND_UNSUPPORTED`.
- The frontend has no DC ID, target address, transport type, relay init, or
  bidirectional transforms.
- WebSocket transform callbacks exist internally, but are populated only for
  the Worker media re-encryption path.
- Direct WS and CF proxy do not accept MTProxy stream transforms.
- TCP fallback has no transform support.

An adapter-only probe would have no real request producer and would therefore
be a fake bridge. No Go interface or production route code was added.

## Decision

Status: UNSUPPORTED_NO_ROUTE_HOOK

Reason:

The local MTProto frontend does not yet perform the upstream-confirmed
handshake/session setup required to produce a DC-aware outbound request, and
the existing route backend has no shared transform-capable connector boundary.

Required future change:

- implement and test the MTProxy handshake/session output first;
- introduce a connector around that concrete output;
- probe one route, preferably direct WS, before extending other routes;
- retain `OUTBOUND_UNSUPPORTED` until end-to-end traffic succeeds.

## Manual Test Plan

No route behavior changed in this version. Before any later route probe:

1. Verify a clean/default install still selects SOCKS5/WS.
2. Verify MTProto continues to show `MTPROTO_LOCAL_ONLY_LIMITED`.
3. Verify a local MTProto connection is rejected as
   `OUTBOUND_UNSUPPORTED`, not reported as connected.
4. Verify route diagnostics remain sourced from the SOCKS5/WS runtime.
5. For the first real route probe, test both mobile and Wi-Fi and keep all
   routes except the selected probe route disabled.
