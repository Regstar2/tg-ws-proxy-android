# v1.10.10 - Go First Route Backend

## Goal

Replace the local-only MTProto listener with one real outbound backend while
leaving the stable SOCKS5/WS route system unchanged.

## Selected backend

Backend: `direct_tcp`

Reason:

- it matches the MTProxy relay stream model directly;
- it requires no Worker or Cloudflare protocol changes;
- it has no implicit fallback;
- it can be tested independently from the SOCKS5 route selector.

## Implementation

The Go MTProto frontend now:

1. Reads the 64-byte MTProxy client init.
2. Derives the secret-based client decrypt/encrypt streams.
3. Validates abridged, intermediate, or padded-intermediate transport.
4. Extracts the signed DC ID and media flag.
5. Generates a separate Telegram relay init.
6. Creates stateful client-to-relay and relay-to-client transforms.
7. Sends a DC-aware request to `mtProtoDirectConnector`.

The connector:

- resolves the canonical IP for the requested DC;
- opens direct TCP port 443;
- writes the relay init;
- returns the stream to the frontend bridge;
- never attempts an alternate backend.

## Route truth

Native status exports:

```text
frontend: MTProto
selected backend: direct_tcp
actual backend: direct_tcp or none
fallback used: false
reason: awaiting_connection / connected / handshake_failed /
        direct_tcp_connect_failed / relay_init_write_failed / connection_closed
```

Capability status:

```text
MTPROTO_ROUTE_DIRECT_READY
```

Listener status:

```text
LISTENING_ROUTE_READY
```

Android maps this to `MtProtoRuntimeState.RUNNING` and
`MTPROTO_ROUTE_DIRECT_READY`. The previous
`MTPROTO_LOCAL_ONLY_LIMITED` state remains available for runtimes without a
connector.

## Safety

- SOCKS5 remains the default frontend.
- `StartProxy`, `runRouteChain`, route strategy, and Worker pool behavior are
  unchanged.
- MTProto has exactly one backend.
- No fallback is performed silently or otherwise.
- Raw proxy secrets are not added to status or logs.
- The connector receives only DC/media/transport, relay init, and stream
  transforms.

## Toolchain

Windows CGO is configured with the existing MSYS2 UCRT64 toolchain:

```text
CGO_ENABLED=1
CC=gcc
CXX=g++
PATH includes C:\msys64\ucrt64\bin
```

The settings are persisted in the user Go environment and user `PATH`. A new
terminal inherits them without per-command overrides.

  - `WorkerFailoverResolverTest.deadWorkerWithBackoffSkipped`
  - `WorkerPoolUiStateMapperTest.maskedUrl_hidesQueryAndSecrets`
- `.\gradlew.bat lint`: PASSED.
- `.\gradlew.bat assembleDebug`: PASSED. Packaging retained the unstripped
  `libtgwsproxy.so`, as in previous builds.

## Manual Test Plan

1. Keep MTProto disabled and verify SOCKS5/WS still starts and connects.
2. Enable MTProto and verify status becomes `MTPROTO_ROUTE_DIRECT_READY`.
3. Apply the generated proxy link in Telegram and verify a connection through
   direct TCP on mobile data.
4. Repeat the direct TCP test on Wi-Fi.
5. Block or disconnect the network and verify
   `direct_tcp_connect_failed`, `actual_backend=none`, and
   `fallback_used=false`.
6. Verify no Worker or CF route is attempted.
7. Verify logs and diagnostics do not contain the raw secret.
8. Stop MTProto, return to SOCKS5, and verify the stable frontend still works.
