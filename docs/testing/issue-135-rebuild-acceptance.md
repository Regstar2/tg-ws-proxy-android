# Issue #135 — независимая реализация маршрутов (v1.11.7)

## Источник

Реализация начата от чистого `main` (`baf61c29e345a604d3915dbcec516cca5bb9a2fc`), а не от предыдущего PR. Пользовательский интерфейс ориентирован на переданный `TGWSProxy_Routes_Revised.html`.

## Видимый экран

В «Настройки → Маршруты» находятся независимые переключаемые профили Wi-Fi и мобильной сети, один список пяти путей с `⋮⋮ → номер → название → ↑↓ → Switch`, счётчик активных маршрутов, цепочка fallback и подтверждение сброса. Отключённые маршруты остаются в конце того же списка. Выключение последнего активного запрещено.

## Регрессия на устройстве: маршрут отсутствует после смены настроек

В логах 2026-11-04 перед сбоем подтверждена двусторонняя передача через CF Proxy. После смены/перезапуска политики Native MTProto зарегистрировал `oldRoutes=direct_ws|cf_proxy_ws newRoutes=none preferred=awg_warp`, а затем `reason=no_mtproto_route_available`. Это доказывает отсутствие кандидатов в runtime, но не доказывает, какая именно операция пользователя или legacy-ветка удалила список.

Защита в ветке:
- Java/Kotlin редактор не позволяет отключить последний **настроенный** исходящий путь, если оставшиеся AWG и Worker не имеют конфигурации; отключённый TCP/Direct не включается скрыто.
- Native MTProto проверяет наличие допустимого исходящего кандидата **до** установки настроек и старта listener, а также до hot-update. Непригодная цепочка отклоняется, существующая работающая конфигурация hot-update не заменяется.
- Если в сохранённом профиле остались только ненастроенные AWG/Worker, приложение должно явно сообщить о невозможности подключения. Для восстановления пользователь выбирает ранее настроенный CF Proxy, Direct WebSocket или TCP fallback; автоматическое включение запрещённого пути не допускается.
- Перетаскивание за ручку `⋮⋮` теперь удерживает визуальный элемент под пальцем, а соседние строки плавно смещаются; отпускание переносит маршрут на любую допустимую позицию, а не только на соседнюю. Изменение применяется один раз на `onDragEnd`.
- Приёмка: через один жест переместить первый маршрут сразу на третье место, проверить новую fallback-цепочку, затем проверить текст и медиа через MTProto с `up_bytes>0` и `down_bytes>0`. Реальное выполнение на телефоне и двусторонняя проверка **ещё не подтверждены**.

## Компактность экрана (исправление по Android-скриншотам)

- Wi-Fi/мобильная сеть выбираются единым сегментированным переключателем Material 3, а не двумя крупными самостоятельными блоками.
- Пять маршрутов находятся **в одной общей карточке** с тонкими разделителями вместо пяти крупных плиток и вертикальных промежутков. Сохраняются порядок `⋮⋮ → № → название → ↑↓ → Switch`, метки тестирования и доступность изменения порядка.
- Названия могут занимать до двух строк на узких экранах; неактивный маршрут остаётся внутри того же списка с подписью. Fallback-блок и нижние действия уменьшены по отступам и типографике.
- UI-тест проверяет, что все пять маршрутов находятся в общей секции. Реальный внешний вид на телефоне, в том числе при увеличенном шрифте, ещё требует подтверждения снимком экрана после установки новой сборки.

## Хранение и миграция

- Вторая версия сохраняется в `route_policy_{wifi|mobile|unknown}_v2` как `active=...;inactive=...;strategy=...`. Источник истины — только `active` и `inactive`; старый strategy сохраняется ради совместимости, но не сортирует маршруты.
- При отсутствии v2 читается соответствующая v1. Валидный `preferred` становится первым; остальные активные перечисляются в детерминированном порядке. При `fallback=0` в активной цепочке остаётся **только один маршрут**, ранее разрешённые резервные маршруты переходят в выключенные.
- Неизвестные ID и дубликаты не попадают в цепочку; повреждённая пустая активная цепочка приводит к безопасному дефолту.
- Если ни v2, ни v1 не сохранены, `EffectiveRoutePolicyResolver` преобразует старый `connection_mode` в политику. Профиль `UNKNOWN` по умолчанию CF-only.
- Сброс выбранного профиля удаляет его устаревшую v1-политику и сохраняет явный v2-снимок значений по умолчанию: так старый глобальный connection_mode не может снова переопределить сброс. Второй профиль остаётся без изменений.

## Реальное применение

`UI → NetworkRoutePolicyEditor → NetworkRoutePolicyRepository → EffectiveRoutePolicyResolver → ProxyRuntimeConfigFactory → @route_order → Go MTProto connector`.

`@route_order` задаёт единственный упорядоченный список для новых сессий MTProto, в том числе test DC. Предпочтения Auto, scores и last-good его не переставляют. Ненастроенный Worker/AWG возвращает ошибку соответствующего маршрута, после которой следующий кандидат выбирается только из явного списка. При одном кандидате скрытого Direct/TCP нет.

Смена профиля текущей сети и редактирование его порядка отправляют `ACTION_RECONFIGURE`. Существующий MTProto frontend **не перезапускается**: `UpdateMtProtoRoutePolicy` обновляет runtime-снимок для будущих подключений. Запрошенная политика сохраняется, а асинхронный результат фиксируется отдельно. Ошибка native hot-apply отображается пользователю; уже установленные соединения не останавливаются намеренно.

**Важно:** стадия `outbound_connected` в native-логе означает только готовый transport/relay-init, а не доказанный двусторонний MTProto-обмен. Фактическую работоспособность текста и медиа подтверждают только данные device smoke (uplink/downlink и пользовательский результат). Повторное использование уже отправленного relay-init другим маршрутом после одностороннего timeout **не заявляется** как реализованное.
