# v1.11.0 — stable AWG/WARP routing

[Русский](v1.11.0.md) · **English**

## About this release

`v1.11.0` is the stable TgWsProxy Android release for Android 8.0+ / `arm64-v8a`. It moves the userspace AWG/WARP route and in-app Consumer WARP profile management from beta to the stable channel.

Metadata: `versionName 1.11.0`, `versionCode 54`.

No manual settings migration is required. `versionCode 54` is greater than `v1.10.14` (52) and `v1.11.0-beta.1` (53), so the stable APK is intended to update both versions when the release signature matches.

## Highlights

- `awg_warp` routes only Telegram connections sent to the local proxy through userspace AmneziaWG/WARP; it does not use Android `VpnService`, root, or a system TUN.
- Automatic profile creation now uses a layered bootstrap path: an already working AWG/WARP profile → direct Consumer API → custom provisioning Workers → the built-in pool.
- The application includes **3 project-provided provisioning Workers**. They are used only for WARP profile generation/activation and never participate in Telegram `cf_worker_ws` traffic.
- Profile validation requires a real Telegram MTProto `req_pq_multi → resPQ` round-trip, followed by a second full-duplex confirmation for an automatically generated candidate.
- Saved profiles can be renamed and edited; an edited config must be validated again.

## Changes

### New connection path: `awg_warp`

Telegram traffic follows this path:

```text
Telegram
  ↓
127.0.0.1:1443 — local MTProto Proxy
  ↓
TgWsProxy native runtime
  ↓
awg_warp
  ↓
userspace netstack + amneziawg-go
  ↓
WARP/AWG tunnel
  ↓
Telegram DC
```

The tunnel exists inside the TgWsProxy process and is used only for connections Telegram sends to the local proxy. Other applications and system traffic are not routed through it.

### Automatic WARP profile provisioning

**Settings → Cloudflare → WARP / AmneziaWG → Create profile** uses this bounded order:

```text
new local WireGuard keypair
        ↓
selected WORKING AWG/WARP profile
        ↓
other WORKING AWG/WARP profiles
        ↓
direct HTTPS → api.cloudflareclient.com
        ↓
enabled custom provisioning Workers
        ↓
3 built-in project provisioning Workers (when enabled)
        ↓
Consumer WARP registration + activation
        ↓
AWG config generation
        ↓
bounded autotune
        ↓
Telegram MTProto req_pq_multi → resPQ
        ↓
second 2/2 confirmation
        ↓
save profile
```

Each automatically generated profile gets a new local keypair and an independent Consumer WARP registration. The private key is not sent to the Consumer API or a bootstrap Worker.

A saved working AWG profile is used only as transport to the fixed `api.cloudflareclient.com` service. This does not expose a general HTTP proxy and does not clone an existing registration.

### Provisioning Workers

Provisioning Workers and normal Telegram Workers are separate:

| Type | Purpose | Telegram traffic | Durable Objects |
|---|---|---:|---:|
| `cf_worker_ws` Worker | MTProto chunk relay to Telegram DC | Yes | Yes for the current chunk-relay design |
| WARP provisioning Worker | Consumer WARP registration/activation only | No | Not required for standalone deployment |

The built-in pool contains three project endpoints. It is enabled by default as a cold-start fallback and can be disabled. When disabled, the app must not contact those endpoints.

Custom provisioning Workers are tried before the built-in pool. A custom endpoint must be a base HTTPS URL without credentials, query/fragment, or an arbitrary path. Compatibility is checked using:

```json
{"service":"warp-bootstrap","revision":"warp-bootstrap-v1"}
```

Allowed protocol:

```text
GET   /warp-bootstrap/health
POST  /warp-bootstrap/v0a4005/reg
PATCH /warp-bootstrap/v0a4005/reg/<registration-id>
```

Full guide for both Worker types: [docs/cloudflare-worker.md](../cloudflare-worker.md).

### Profiles

- multiple saved WARP/AWG profiles;
- one explicitly selected profile;
- automatic Consumer WARP provisioning and manual `.conf` import;
- profile name/config editing;
- generated names `WARP 1`, `WARP 2`, ...;
- `PrivateKey` hidden from normal UI/support-safe diagnostics;
- revalidation required after editing the config.

## Installation and updating

### New installation

Download:

```text
TgWsProxy-Android-v1.11.0-arm64-v8a.apk
```

Requirements: Android 8.0+ and `arm64-v8a`.

### Updating

The stable APK is intended to install over signed `v1.10.14` and `v1.11.0-beta.1`. Settings and app-private WARP profiles should remain intact during a normal same-signature update.

Do not uninstall the application to bypass a signature error because uninstalling removes app-private data.

The Updates screen checks the official GitHub Releases feed and opens the release page. It does not perform a silent self-update.

## Verification

The `v1.11.0` tag release workflow is configured to rerun `scripts/ci.ps1`, build the signed APK, verify package/version metadata and the APK signature, and only then create the GitHub Release.

A manual signed-APK device smoke test of the current stable candidate remains a pre-tag gate and must be recorded in [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md). Beta acceptance results are not presented here as a repeat verification of the stable source.

## Known issues

- Consumer WARP registration depends on an external Cloudflare API; its availability and rate limits are outside the app's control.
- On a fresh install without a working AWG profile, an unavailable direct Consumer API requires a custom or permitted built-in provisioning Worker.
- When the user disables the built-in pool, the application does not use the three project endpoints as a hidden fallback.
- `cf_worker_ws` depends on Cloudflare Workers/Durable Objects and is generally slower than direct routes.
- Only `arm64-v8a` is supported.
