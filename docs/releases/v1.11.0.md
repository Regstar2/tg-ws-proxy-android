# v1.11.0 — stable AWG/WARP routing

**Русский** · [English](v1.11.0_EN.md)

## О релизе

`v1.11.0` — stable-релиз TgWsProxy Android для Android 8.0+ / `arm64-v8a`. Версия переводит userspace AWG/WARP route и встроенное управление Consumer WARP-профилями из beta в основной канал.

Метаданные: `versionName 1.11.0`, `versionCode 54`.

Формат настроек приложения не требует ручной миграции. `versionCode 54` выше `v1.10.14` (52) и `v1.11.0-beta.1` (53), поэтому stable APK предназначен для обычного обновления поверх обеих версий при той же release-подписи.

## Главное

- `awg_warp` передаёт только Telegram-соединения локального proxy frontend через userspace AmneziaWG/WARP; Android `VpnService`, root и system TUN не используются.
- Автоматическое создание профиля получило многоступенчатый bootstrap: уже рабочий AWG/WARP-профиль → direct Consumer API → custom provisioning Workers → встроенный pool.
- В приложение встроены **3 project-provided provisioning Worker**. Они используются только для генерации/активации WARP-профиля и не участвуют в Telegram `cf_worker_ws`.
- Проверка профиля требует реальный Telegram MTProto `req_pq_multi → resPQ`, после чего автоматический кандидат подтверждается второй full-duplex проверкой.
- Профили можно переименовывать и редактировать; изменённый config требуется проверить заново.

## Изменения

### Новый путь подключения: `awg_warp`

Путь Telegram traffic выглядит так:

```text
Telegram
  ↓
127.0.0.1:1443 — локальный MTProto Proxy
  ↓
TgWsProxy native runtime
  ↓
awg_warp
  ↓
userspace netstack + amneziawg-go
  ↓
WARP/AWG tunnel
  ↓
Telegram DC
```

Туннель существует внутри процесса TgWsProxy и применяется только к соединениям, которые Telegram отправляет в локальный proxy. Остальные приложения и системный трафик через него не перенаправляются.

### Автоматическое создание WARP-профиля

Команда **Настройки → Cloudflare → WARP / AmneziaWG → Создать профиль** запускает следующий порядок:

```text
новая локальная WireGuard keypair
        ↓
выбранный WORKING AWG/WARP-профиль
        ↓
другие WORKING AWG/WARP-профили
        ↓
direct HTTPS → api.cloudflareclient.com
        ↓
enabled custom provisioning Workers
        ↓
3 built-in project provisioning Workers (если разрешены)
        ↓
Consumer WARP registration + activation
        ↓
формирование AWG config
        ↓
bounded autotune
        ↓
Telegram MTProto req_pq_multi → resPQ
        ↓
повторное подтверждение 2/2
        ↓
сохранение профиля
```

Каждый новый автоматический профиль получает новую private/public keypair на устройстве и отдельную Consumer WARP registration. Private key не передаётся Consumer API или bootstrap Worker.

Рабочий сохранённый AWG-профиль используется только как транспорт до фиксированного `api.cloudflareclient.com`; это не универсальный HTTP proxy и не клонирование старой registration.

### Provisioning Workers

Provisioning Worker и обычный Telegram Worker — разные сущности:

| Тип | Назначение | Telegram traffic | Durable Objects |
|---|---|---:|---:|
| `cf_worker_ws` Worker | MTProto chunk relay до Telegram DC | Да | Да, для текущей chunk-relay схемы |
| WARP provisioning Worker | Только Consumer WARP registration/activation | Нет | Не требуется для standalone deployment |

Встроенный pool содержит три endpoint проекта. Он включён по умолчанию как cold-start fallback, но пользователь может отключить его. При выключенном toggle приложение не обращается к встроенным endpoint.

Custom provisioning Workers имеют приоритет над встроенными. Для custom endpoint разрешён только базовый HTTPS URL без credentials, query/fragment и произвольного path. Перед использованием приложение проверяет:

```json
{"service":"warp-bootstrap","revision":"warp-bootstrap-v1"}
```

Разрешённый protocol:

```text
GET   /warp-bootstrap/health
POST  /warp-bootstrap/v0a4005/reg
PATCH /warp-bootstrap/v0a4005/reg/<registration-id>
```

Полный гайд по обоим типам Worker: [docs/cloudflare-worker.md](../cloudflare-worker.md).

### Профили

- несколько сохранённых WARP/AWG-профилей;
- один явно выбранный профиль;
- automatic Consumer WARP provisioning и ручной импорт `.conf`;
- редактирование имени и config;
- имена automatic profiles `WARP 1`, `WARP 2`, ...;
- безопасное скрытие `PrivateKey` в обычном UI/diagnostics;
- повторная validation после изменения config.

## Установка и обновление

### Новая установка

Скачайте из GitHub Releases:

```text
TgWsProxy-Android-v1.11.0-arm64-v8a.apk
```

Требования: Android 8.0+ и `arm64-v8a`.

### Обновление

Stable APK предназначен для установки поверх подписанных `v1.10.14` и `v1.11.0-beta.1`. Настройки и app-private WARP-профили должны сохраняться при обычном обновлении поверх приложения с той же подписью.

Не удаляйте приложение для обхода ошибки подписи: uninstall удаляет app-private данные.

Встроенный экран Updates проверяет официальный GitHub Releases feed и открывает страницу релиза; silent self-update не выполняется.

## Проверено

Публикация tag `v1.11.0` настроена так, что release workflow повторно запускает `scripts/ci.ps1`, собирает signed APK, проверяет package/version metadata и APK signature и только затем создаёт GitHub Release.

Ручной signed-APK device smoke текущего stable candidate остаётся pre-tag gate и должен быть зафиксирован в [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md). Результаты beta acceptance не выдаются здесь за повторную проверку stable source.

## Известные проблемы

- Consumer WARP registration зависит от внешнего API Cloudflare; доступность и rate limits не контролируются приложением.
- На fresh install без рабочего AWG-профиля при недоступном direct Consumer API потребуется custom либо разрешённый built-in provisioning Worker.
- Если пользователь отключил built-in pool, приложение не использует три встроенных project endpoint как скрытый fallback.
- `cf_worker_ws` зависит от Cloudflare Workers/Durable Objects и обычно медленнее прямых маршрутов.
- Поддерживается только ABI `arm64-v8a`.
